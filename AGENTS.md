## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

This app is a single game screen with in-app tabs (`src/ui/App.tsx`), so it does not use Expo Router. Add Expo Router only if real multi-screen navigation is needed.

## Project rules

- One codebase, many games. Never branch on a game id in code: everything game-specific belongs in `games/<id>/game.json` and the schema in `src/config/schema.ts` / `schema.sim.ts` (with cross-field checks in `lintGameConfig`, `src/config/lint.ts`).
- One game per bundle, three levels of code (`scripts/lib/modes.js`, table in `docs/design/space-bundle.md`): (a) shared by every game (`SHARED_UI` under `src/ui`, `SHARED_SRC` for the rest of `src/`): no drawn art of any game, no screens of any game, no game words; (b) a family (`FAMILIES.tabs`: the tab shell, header, list homes, meta screens and the first game's drawn kit, for sim and classic only); (c) a mode's folders (`src/modes/<mode>/`, `src/ui/sim/`, `src/ui/scene/`, `src/ui/haul/`, `src/ui/merge/`, `src/ui/decree/`, haul's rules and schema: `src/engine/haul.ts`, `src/engine/haul/`, `src/engine/haulMode.ts`, `src/engine/loadout.ts`, `src/engine/fixtures/haul.ts`, `src/config/schema.haul.ts`, and merge's: `src/engine/merge.ts`, `src/engine/merge/`, `src/engine/mergeMode.ts`, `src/engine/fixtures/merge.ts`, `src/config/schema.merge.ts`, `src/config/merge.content.ts`, and decree's: `src/engine/decree.ts`, `src/engine/decree/`, `src/engine/decreeMode.ts`, `src/engine/fixtures/decree.ts`, `src/config/schema.decree.ts`, `src/config/decree.content.ts`), reached only through the generated entry `src/generated/mode.ts`. A shared file imports only shared files; a family file only its family and shared files; a mode only itself, its families and shared files. What a shared piece needs from a mode (portraits, the tutorial pointer, "art:" icons, the hint script) the entry hands over at install (`src/modes/contract.ts`). A new file or folder anywhere in `src/` must be listed in `modes.js` or the check fails; imports are relative paths or installed packages (an import the check cannot resolve fails). `src/modes/entries.test.ts` pins what the sim, classic, haul, merge, decree and salvage entries hand over: keep it in step. Node-only files (`NODE_ONLY`: the fx catalogues, `src/config/artIcons.ts`, `src/config/lint.ts`) are never imported by the app (so they may read any mode's files). A mode's own game.json block that needs its own schema stays opaque in the shared schema and is parsed by the mode's engine at install (`EngineMode.config`; haul: `src/config/schema.haul.ts` is a haul file). A game gets only its own sound pack (`shared/sfx/<pack>/`, game.json `soundPack`, required; `null` means no shared pack, only `games/<id>/assets/sfx/`, as Orbit Haulers does). A haul game's fx table comes from its own catalogue `src/services/fx/catalog.haul.ts`, a merge game's from `src/services/fx/catalog.merge.ts` (the shared keys the store plays are mapped onto it in `src/modes/merge/soundKeys.ts`), a decree game's from `src/services/fx/catalog.decree.ts` (mapped in `src/modes/decree/soundKeys.ts`). Another mode's theme words in a shared or family string fail the check unless listed in `scripts/lib/themeWords.allowed.json` (the known remainder: never add text a player reads). Another game's names and lines (cards, modules, characters, call signs, venues, galaxies, buyers, story lines, store sentences) in any file of a bundle fail the check too (the string denylist; `scripts/bundle-allow.json` only for engine identifiers no player reads). Run `npm run check:bundle` (`-- --words` lists every such word; `-- --export` before a release: it exports in a copy of the project and writes `games/<id>/store/bundle-report.json`, fingerprint dimension 8; `npm run scan:binary -- <file> --game <id>` on the store binary).
- Rules of a mode that does not run on the built-in sim and classic rules are an `EngineMode` (`src/engine/mode.ts`) the mode's entry hands over (`engine`); the shared engine delegates to it through `engineFor(cfg)` and runs its old code when none is installed (`src/engine/modeRegression.test.ts` must stay green, its recordings never re-recorded). Shared engine files never import a mode's rules (`economy.ts` never imports `loadout.ts` or `haul*`).
- The merge mode (Lantern Row, `games/night-market`): its rules are specified in `docs/design/market-design.md`, whose section 11 (the lead's decisions) overrides the body; its numbers live in `src/config/merge.content.ts` and are tuned and written into game.json by `scripts/content/build-night.py` with the balance bot (`scripts/content/merge-bot.ts`, `src/engine/merge/bot.ts`); a screen never computes a price, a rate, odds or a time itself (it asks the rules through `src/engine/merge.ts`) and every amount of coins shown or paid goes through `roundCoins`.
- The decree mode (Proudly Adequate, `games/high-office`): its rules are specified in `docs/design/office-design.md`, whose section 11 (the lead's decisions) overrides the body; its numbers live in `src/config/decree.content.ts` and are tuned and written into game.json by `scripts/content/build-office.py` with the balance bot (`scripts/content/decree-bot.ts`, `src/engine/decree/bot.ts`); a screen never computes a price, a rate, a share or a time itself (it asks the rules through `src/engine/decree.ts`), every amount of dibs shown or paid goes through `roundDibs`, and what a paper prints is exactly what is applied (the numbers are frozen when the paper lands). Its written content (about 1,800 strings) lives in the authoring files `scripts/content/office/*.json`, written to the style sheet `docs/design/office-style.md` and merged into game.json by the same script: everything in it is invented (no real person, party, country, movement or live issue; the jokes are on office and on the player's own character), every proper noun is registered in `scripts/content/office/names.json`, and every text must pass `npx tsx scripts/content/office/check.ts --all` (format, fit on a small phone, the satire lint) before it ships; the lint catches words, not tone, so a changed or new text is also read by a person.
- The salvage mode (Scrap to Ingot, `games/scrap-yard`, landscape): its first yard is specified in `docs/design/yard-stage1.md` (section 12 lists what the review of the built game changed) under `docs/design/yard-design.md`; the lead's decisions in `docs/design/yard-decisions.md` (the economy E1 onwards, the map M1 to M7, the rulings on the review) outrank both. Its folders are a mode's (level c): `src/modes/salvage/`, `src/ui/salvage/`, `src/engine/salvage.ts` (the facade the screens ask), `src/engine/salvage/`, `src/engine/salvageMode.ts`, `src/engine/fixtures/salvage.ts`, `src/config/schema.salvage.ts`, `src/config/salvage.content.ts`. Its numbers and its map live in `src/config/salvage.content.ts` and are written into game.json by `scripts/content/build-yard.py` (its `--check` also runs the map checker `scripts/content/yard_map.py`), tuned with the balance bot (`scripts/content/yard-bot.ts`, `src/engine/salvage/bot.ts`; the last measurement is `docs/design/yard-bots.md`); a screen never computes a price, a rate, a mass, a time or a coordinate itself (it asks the rules through `src/engine/salvage.ts` and formats with its formatters), what a card or a ticket shows is exactly what is applied, and time away is paid once inside the state. Things and pieces are whole items, loose material is grams, crew are agents on dated legs, and a tick, a jump and time away are one function (`src/engine/salvage/tickjump.test.ts` must stay green). Its interface words live in `src/ui/salvage/strings.ts` with the key list `src/engine/salvage/textKeys.ts` and the authoring file `scripts/content/yard/text.json` (`npx tsx scripts/content/yard/check.ts --all`); every invented name (the yard, the merchant, partners, rivals, the currency) comes from the register `scripts/content/yard/names.json` by id (`python3 -I scripts/content/yard/build-ids.py --check`), never as a literal. Its art is drawn in code (`src/ui/salvage/art/`, baked into atlas sheets; the yard view draws runs of one sheet, at most twenty atlas draws a frame); its fx table comes from its own catalogue `src/services/fx/catalog.salvage.ts` (mapped in `src/modes/salvage/soundKeys.ts`); its store listing is `scripts/content/yard-store.json` (copied into game.json by `build-yard.py`). Stage 2 (the works, the bank, the shop; `docs/design/yard-stage2.md`) is in the code but dark: content `release.stage` is 1 until its screens exist, and at 1 nothing of stage 2 opens, shows or is saved (`SalvageSchema`'s `stageView`). The yard view and the rules never disagree on who sits in the truck: a presence sample's `driving` flag seats the boss whenever the truck stands free (`src/engine/salvage/hand.ts` `seatByFlag`), and the frame loop takes the rules' `truck.by` back (`src/ui/salvage/world/frameLoop.ts`, "who sits in the cab"; part 6 section 18.3 of `yard-decisions.md`): change one side only with the other.
- `src/engine/` stays pure TypeScript: no React, no native imports, deterministic. Never call `Math.random` or `Date.now` there; time comes in as `now`, randomness from the seed in state (`rng.ts`). Every engine change comes with tests (`npm test`).
- All game state changes go through actions in `src/state/store.ts`; UI components never mutate state or call engine functions that change it on their own.
- Sound and haptics only through the fx service (`src/services/fx`, `fx.play('<key>')` with keys from `catalog.ts`); never import expo-audio or expo-haptics elsewhere. The app never imports `catalog.ts` at run time (only its types): it plays the generated per-mode table.
- Characters are drawn in code: use `"char:<id>"` icons with a look in the game's top-level `cast`, not new image assets, unless the game has its own art.
- Native SDKs are only required from `src/services/sdks.ts` (web uses `sdks.web.ts`).
- zustand selectors that return new objects or arrays must use `useShallow`. The store's `game` changes ten times a second: select the few values a component shows, never the whole object in lists or animated components.
- Animation runs on the UI thread (Reanimated shared values, Skia). Code there ("worklets") may only call other worklets: this crashes on phones but never in the web preview, so run `npm run lint:worklets`. Never free a Skia picture or image a mounted canvas may still draw; nothing invisible may keep animating.
- Never one Skia canvas per list row: portraits and `art:` icons go through `GameIcon`, which shows cached images.
- Every dialog is the kit `Sheet` (or registers with `useOverlay`): one dialog at a time, and popups, the tutorial hand and story dialogs wait for it (`src/state/overlays.ts`).
- Controls a hint can point at register with `useTarget(key)` (`src/ui/hints/targets.ts` lists the keys).
- A haul game's interface words live in one file, `src/ui/haul/strings.ts`, a merge game's in `src/ui/merge/strings.ts`, a decree game's in `src/ui/decree/strings.ts` (the fingerprint and the voice check read them): no word stays in a component, a fallback or another string file. Names of things come from game.json.
- Text on a coloured fill uses `textOn(fill)`; a stage or rarity colour used as text goes through `inkOf` (`src/ui/theme.ts`).
- Text in a bar of fixed height (the header) is sized by hand from `useWindowDimensions().fontScale` with `allowFontScaling={false}`, in rows whose heights add up (`src/ui/components/headerMetrics.ts`), never with negative margins. Never give a `TextInput` (so `RollingNumber`) a `lineHeight`: an iPhone draws the text at the bottom of the line, on top of whatever is under it, and the web preview does not show it.
- Shipped games' numbers come from `scripts/content/build-*.py`; change the script and regenerate, never hand-edit those tables. Each game needs its own economy table (`validate` rejects copies).
- Chests are earned, not sold, unless a game sets `meta.chestsForSale`; deals never contain permanent items; offer timers are real.
- Store texts: Orbit Haulers' listing is `scripts/content/space-store.json` (copied into game.json by `build-space.py`), Lantern Row's is `scripts/content/night-store.json` (copied by `build-night.py`), Proudly Adequate's is `scripts/content/office-store.json` (copied by `build-office.py`); release notes and the release log are `games/<id>/store/releases.json`; App Review notes `games/<id>/store/REVIEW-NOTES.md`. Run `npm run sync` after changing any of them (validate fails on stale store files). Before a submission: `npm run validate:release` (every fingerprint dimension known, real app ids, release notes for the version).
- Before declaring done: `npm run typecheck`, `npm test`, `npm run validate`, `npm run lint:worklets`, `npm run check:bundle`, and look at what you changed in the web preview (`src/dev/devtools.web.ts` lists the switches). Development tools of the web preview live in `.web.ts` files whose phone twins hold nothing (`devtools`, `presets`, `devViews`); `scripts/lib/modes.js` `WEB_ONLY` lists what no phone bundle may hold.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
